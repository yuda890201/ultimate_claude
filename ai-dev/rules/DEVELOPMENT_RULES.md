## 0. 大原則（これだけは必ず守る）

| # | 原則 | ひとことで言うと |
|---|---|---|
| 1 | **GitHub が唯一の正本** | 手元のファイルは作業用コピー。pushして初めて「存在する」 |
| 2 | **今どこを触っているか必ず確認** | リポジトリ名・ブランチ名・GCPプロジェクト名を作業前に声に出す |
| 3 | **壊す操作は必ず事前確認** | 削除・強制上書き・本番デプロイは、プロジェクトオーナーの承諾なしに実行しない |
| 4 | **秘密情報は絶対にGitHubへ書かない** | APIキー・パスワード・トークン・認証JSONは1文字も置かない |
| 5 | **迷ったら止まって聞く** | 推測で進めるより、確認して止まる方が常に安い |

## 1. GitHub を唯一の正本とする

### 1-1. 基本の流れ

```
GitHub（正本）
  ↓ clone / pull
作業環境（Cloud Shell など）
  ↓ AIによる編集
テスト・ビルド
  ↓ commit
  ↓ push
GitHub（正本が更新される）
```

### 1-2. 守ること

- 手元にあるファイルは**すべて作業用コピー**です。正本ではありません。
- 作業環境は壊れても作り直せます。**GitHubに push されていない変更は、失われても文句を言えません。**
- 作業を終えるときは、必ず「GitHubに反映されているか」を確認してください（→ 第4章）。
- GitHubのコードと手元のコードが食い違っている場合、**原則としてGitHubが正しい**とみなします。手元の変更を優先したい場合は、理由を説明してから push してください。

## 2. 作業環境とリポジトリの配置ルール

### 2-1. 作業環境は2種類あります（混同しないこと）

| 環境 | 特徴 | ホームの場所 | `gcloud` | 永続性 |
|---|---|---|---|---|
| **Google Cloud Shell** | プロジェクトオーナーが普段使う環境。GCP操作ができる | `~/ai-dev/` | ✅ 使える | ✅ 残る |
| **Claude Code リモート環境** | claude.ai から起動する使い捨てコンテナ | `/home/user/` にリポジトリが並ぶ | ❌ 無い | ❌ **セッション終了で消える** |

**重要**: Claude Code リモート環境で作ったファイルは、**push しなければ消滅します**。
また、この環境には `gcloud` も `gh` も入っていないため、**Cloud Run や Firebase への実デプロイはできません**。デプロイは Cloud Shell 側で行ってください。

### 2-2. Cloud Shell でのディレクトリ構成

```
~/ai-dev/
├── projects/     ← GitHubからcloneしたアプリを置く場所
│   ├── family-quest/
│   ├── vcv/
│   └── ...
├── rules/        ← 共通ルール（このファイル）
├── templates/    ← GEMINI.md / CLAUDE.md のひな形
├── skills/       ← AI用スキル
├── scripts/      ← 安全装置スクリプト
├── logs/
└── config/
```

`~/ai-dev/` の `rules/` `templates/` `skills/` `scripts/` は、**`ultimate_claude` リポジトリの `ai-dev/` ディレクトリが正本**です。
Cloud Shell 側では、このリポジトリを clone して使います（セットアップ手順は `ai-dev/README.md` を参照）。

### 2-3. clone するときのルール

```bash
cd ~/ai-dev/projects        # ← 必ずここに移動してから
git clone https://github.com/yuda890201/<リポジトリ名>
```

- **すでに同じリポジトリが存在する場合、別の場所に clone しないでください。** 既存のものを `git pull` して使ってください。
- 同じアプリが2箇所にあると、「どちらが最新か分からない」という事故の原因になります。
- 迷ったら `ls ~/ai-dev/projects` で既存を確認してください。

## 3. 作業開始時の確認（全AI共通・省略禁止）

**コードを1行でも変更する前に、以下をすべて実行して結果を報告してください。**

```bash
# 1. 今どこにいるか
pwd

# 2. どのリポジトリか（これが目的のアプリか必ず目視確認）
git remote -v

# 3. どのブランチか
git branch --show-current

# 4. 前のAIが残した未コミット変更は無いか
git status

# 5. GitHubの最新を取得
git fetch origin

# 6. 手元とGitHubがズレていないか
git log --oneline HEAD..origin/main     # GitHubにあって手元に無いもの
git log --oneline origin/main..HEAD     # 手元にあってGitHubに無いもの

# 7. 他のAIが作った、まだmainにマージされていないブランチが無いか
git fetch --all
git branch -r
```

### 3-1. 結果の判断表

| 状況 | 意味 | やること |
|---|---|---|
| `git status` がクリーン、ズレ無し | 正常 | そのまま作業開始 |
| `git status` に未コミット変更がある | **前のAIが作業を終えていない可能性** | ⚠️ **止まってプロジェクトオーナーに報告**。勝手に消さない・勝手にコミットしない |
| GitHubにあって手元に無い | 手元が古い | `git pull origin main` して最新化 |
| 手元にあってGitHubに無い | **push忘れの可能性** | ⚠️ **止まって報告**。内容を確認してから push |
| `main`にはズレが無いが、`git branch -r` に見慣れないブランチがある | **他のAIの未マージ作業がある可能性** | ⚠️ そのブランチの内容(`git log main..origin/<ブランチ名>`)を確認してから作業する。自分の作業と競合しそうならプロジェクトオーナーに確認する |

### 3-2. AI間リレーでの事故防止（最重要）

この環境は Gemini → Claude → Gemini → Claude とリレーで開発します。
最も起きやすい事故は、

> **「Claudeが修正したのに push されていない状態で、Geminiが古いコードを触ってしまう」**

です。これを防ぐため、次を徹底してください。

- **作業を引き継ぐ側（次のAI）**: 上記 3. のチェックを必ず実行する。未コミット変更や未push変更を見つけたら、**作業を始めずに報告する**。`main` だけでなく、**リモートの全ブランチ**（`git branch -r`）も確認する（3-3参照）。
- **作業を終える側（前のAI）**: 第4章の終了確認を必ず実行し、push完了まで見届ける。**「コミットしました」で終わらせない。「pushしました」まで確認する。**
- 引き継ぎ時は、次の3点を必ず報告文に書く：
  1. 編集したリポジトリ名
  2. 作業したブランチ名
  3. push済みコミットのハッシュ（`git rev-parse --short HEAD`）

### 3-3. 【重要な限界】pushしなければ、次のAIには何も見えない

Gemini と Claude は、多くの場合**別々の環境・別々の作業コピー**（Cloud Shellの`~/ai-dev/projects/`と、Claude Codeのリモート環境など）を使います。この場合、

- **前のAIが commit すらしていない作業中のファイル** → 次のAIからは一切見えません（同じ作業コピーを再利用する場合を除く）
- **commit はしたが push していない変更** → GitHub上にも痕跡が残らないため、次のAIが `git fetch` しても**何も検出できません**
- **push はしたが、まだ`main`にマージされていないブランチ** → `main` だけを見ていると見落としますが、`git branch -r` でリモートの全ブランチを確認すれば検出できます

つまり、**「commitしたら必ずpushする」という第4章のルールは、単なる推奨ではなく、
これが守られない限り事故を検知する手段が一切無い、という意味で絶対条件です。**

このため、以下を徹底してください。

- 作業はできるだけ小さく区切り、**区切りのたびに commit → push まで完了させる**。作業を持ち越さない。
- 長時間 push せずに作業を続けない。
- 自分の作業がまだ `main` にマージされていない間は、**ブランチ名と内容を必ず引き継ぎ報告に書く**（3-2の3点）。次のAIが `git branch -r` で見つけても、何の作業か分からなければ確認の手間が増えるため。
- 将来的には、この「pushし忘れ」自体をプログラム側で検知する仕組み（STEP 6の安全装置）を検討する。ルールを読んでいれば防げる、という前提だけに頼らない。

## 4. 作業終了時の確認（全AI共通・省略禁止）

**「終わりました」と報告する前に、以下を必ず実行してください。**

```bash
# 1. 未コミットのものが残っていないか
git status

# 2. 未pushのものが残っていないか（何も出なければOK）
git log --oneline origin/<ブランチ名>..HEAD

# 3. 最終的な状態
git log -1 --oneline
git branch --show-current
```

### 4-1. 終了報告に必ず含める内容

```
【作業完了報告】
- リポジトリ : <リポジトリ名>
- ブランチ   : <ブランチ名>
- コミット   : <ハッシュ> <コミットメッセージ>
- push状態   : 完了 / 未完了（未完了なら理由）
- 未コミット : 無し / あり（あれば内容）
- 変更ファイル: <一覧>
- テスト結果 : <実行した内容と結果>
- 次のAIへの申し送り: <あれば>
```

`git status` がクリーンで、未push が0件でなければ、**作業は完了していません**。

## 5. commit / push のルール

### 5-1. commit

- **意味のある単位でコミットする。** 「いろいろ修正」のような巨大な1コミットは避ける。
- コミットメッセージは**日本語でOK**。何を・なぜ変えたかを1行目に書く。

```
fix: シフト表の日付が1日ずれる問題を修正
feat: 買い物リストに数量入力欄を追加
docs: 共通開発ルールを追加
```

- `git add .` を使う前に、必ず `git status` で**何が追加されるか目視確認**してください。意図しないファイル（`.env`、ログ、`node_modules` など）が混ざる事故を防ぎます。

### 5-2. push

```bash
git push -u origin <ブランチ名>
```

- ネットワークエラーで失敗した場合のみ、最大4回まで再試行（2秒 → 4秒 → 8秒 → 16秒待って再実行）。
- **`git push --force` / `git push -f` は禁止です。** 実行前に必ずプロジェクトオーナーへ確認してください。他の人・他のAIの作業を消してしまう可能性があります。

### 5-3. ブランチ

- 原則として `main` に直接コミットせず、**作業用ブランチ**を切ってください。

```bash
git checkout -b claude/<作業内容>-<日付>     # Claudeの場合
git checkout -b gemini/<作業内容>-<日付>     # Geminiの場合
```

- ブランチ名の先頭に `claude/` `gemini/` を付けることで、**どのAIの作業か一目で分かります**。
- push したら **Pull Request を作成**してください。PRは原則として **draft（下書き）** で作成し、プロジェクトオーナーが確認してからマージします。

### 6-1. 操作前の3点確認

```bash

```

**`git remote -v` で表示されたURLが、依頼されたアプリのものと一致しているか**を必ず目視確認してください。

## 7. Google Cloud に関するルール

### 7-1. GCPプロジェクトとGitHubリポジトリは別物です

- GCPプロジェクトを切り替えても、**編集対象のコードが変わるわけではありません。**
- 逆に、GitHubリポジトリを切り替えても、**GCPプロジェクトは自動で切り替わりません。**
- この2つを混同すると、**別のアプリの本番環境を壊す**ことになります。
- 複数のGCPプロジェクトを素早く安全に切り替える方法（`gcloud config configurations`）は
  `ai-dev/rules/MOBILE_SETUP.md` の第4章を参照してください。

### 7-2. GCP操作の順序（この順番を必ず守る）

```bash
# 1. 今どのGCPプロジェクトにいるか
gcloud config get-value project

# 2. そのプロジェクトのCloud Runサービス一覧
gcloud run services list --region asia-northeast1

# 3. 対象アプリとGCPプロジェクトの対応が正しいか確認
#    → 各アプリの CLAUDE.md / GEMINI.md の「プロジェクト固有情報」欄(2-5)に
#      記載されたGCPプロジェクトIDと、手順1の出力を突き合わせる

# 4. 一致しなければ、その場で操作を中止し、確認する
#    一致した場合のみ、操作を続行する
```

### 7-3. 禁止事項

- 別のGCPプロジェクトを**確認なしに変更しない**
- 本番の Cloud Run サービスを**確認なしに削除しない**
- トラフィック配分（`--traffic`）を**確認なしに変更しない**
- 稼働中のサービスへ**確認なしにデプロイしない**

### 7-4. 判明している設定（参考）

| 項目 | 値 |
|---|---|
| GCPプロジェクト（app-ryosan） | `yuda-store-ai-1788800335` |
| リージョン | `asia-northeast1` |

> 他のアプリのGCPプロジェクトは未確認です。各アプリのMDファイルに記録していってください。

## 8. デプロイ前の確認

### 8-1. このリポジトリ群には4種類のデプロイ方式があります

**アプリごとに方式が違います。「Cloud Runへデプロイ」で統一されていません。**
作業前に、そのアプリがどの方式か必ず確認してください。

| 方式 | 見分け方 | 該当アプリ |
|---|---|---|
| **Cloud Run** | `Dockerfile` がある | `app-ryosan`, `app-studio`, `family-quest` |
| **Firebase** | `firebase.json` がある | `FF_manage`, `kinko-app`, `kitte_manage`, `shift-management-app`, `store-communication-app`, `store-feedback` |
| **GitHub Pages** | `.github/workflows/` にPages設定 | `bunseki-tool`, `store-communication-app` |
| **静的HTML / ビルド不要** | `index.html` のみ | `vcv`, `guchi-app`, `my-instant-app`, `work_schedule` ほか |

### 8-2. Cloud Run デプロイ前チェック

1. 正しいディレクトリから実行しているか（サブディレクトリから `--source .` しない）
2. `gcloud config get-value project` が対象アプリのものか
3. リージョンは `asia-northeast1` か
4. `PORT` 環境変数を使っているか（Cloud Run はポートを指定してきます）
5. ローカルで Docker ビルドと起動確認ができているか
6. **`--allow-unauthenticated` を使っていないか**（認証必須でデプロイする）
7. 秘密情報は `--set-env-vars` ではなく **`--set-secrets`（Secret Manager）** を使っているか
8. デプロイ前の Git チェックポイント（コミット or タグ）を作ったか
9. 失敗したときの戻し方（前のリビジョン名）を控えたか

> `app-ryosan` には `scripts/predeploy-check.sh` という自動チェックスクリプトがあります。同様の仕組みを他アプリにも展開予定です。

### 8-3. Firebase デプロイ前チェック

1. `firebase projects:list` / `firebase use` で**対象プロジェクトが正しいか**
2. Firestore のセキュリティルールを緩めていないか（`allow read, write: if true;` は原則禁止）
3. ルール変更は GitHub Actions 経由で行われるアプリがあるため、**手動デプロイと二重にならないか**確認

### 8-4. デプロイ後

- 実際にURLを開いて動作を確認する
- 壊れていたら、**すぐに前のリビジョンへ戻す**（Cloud Run の場合 `gcloud run services update-traffic`）
- 結果をプロジェクトオーナーへ報告する

## 9. テスト・ビルドの実施

**「たぶん動く」で push しないでください。** 必ず実際に確認してください。

| アプリの種類 | 最低限やること |
|---|---|
| 静的HTML（`index.html` のみ） | ブラウザで開いて動作確認。JSの構文エラーが無いか確認 |
| Node.js / npm プロジェクト | `npm install` → `npm run build` → `npm test`（存在するもののみ） |
| Next.js | `npm run build` が通ること（型エラー・ビルドエラーは push 前に解消） |
| Docker / Cloud Run | `docker build` が通り、ローカル起動して疎通することを確認 |
| Firebase ルール変更 | ルールの構文チェック。可能ならエミュレータで確認 |

- テストが無いアプリでも、**変更した箇所を実際に動かして確認**してください。
- 確認できなかった場合は、**「確認できていない」と正直に報告**してください。黙って push しないこと。

## 10. 秘密情報の取り扱い（違反したら即アウト）

### 10-1. GitHub に絶対に書かないもの

- APIキー、APIトークン
- パスワード、PINコード
- Firebase の秘密鍵、サービスアカウントJSON
- OAuth のクライアントシークレット
- データベースの接続文字列（認証情報付き）
- 個人情報（従業員の氏名・連絡先など）

**これは `.md` ファイル（CLAUDE.md / GEMINI.md 含む）も対象です。** 「メモ代わりに」も禁止です。

### 10-2. 正しい置き場所

| 用途 | 置き場所 |
|---|---|
| Cloud Run の秘密情報 | Google Secret Manager（`--set-secrets` で渡す） |
| ローカル開発 | `.env` ファイル（**必ず `.gitignore` に入れる**） |
| GitHub Actions | GitHub の Secrets 機能 |

### 10-3. もし間違えて push してしまったら

1. **すぐにプロジェクトオーナーへ報告してください**（隠さない）
2. そのキー・トークンを**無効化（revoke）してから**、新しいものを発行する
3. ファイルを消すだけでは Git の履歴に残るため、**キーの無効化が必須**です

### 10-4. コミット前の確認

```bash
git status          # 意図しないファイルが無いか
git diff --cached   # 実際に何を追加するのか中身を見る
```

`.env` `*.key` `*-credentials.json` `serviceAccount*.json` が含まれていたら、**絶対にコミットしない**。

## 11. Gemini と Claude の役割分担

### 11-1. 基本の役割

| | Gemini | Claude |
|---|---|---|
| **主担当** | 新規アプリ開発 | 致命的な不具合の修正 |
| | 機能追加 | 複雑なバグの原因調査 |
| | UI/UX 改善 | コードの問題分析 |
| | ブラッシュアップ | リファクタリングの安全性検証 |
| | リファクタリング | セキュリティ上の問題対応 |
| **共通** | テスト実施 / GitHubへの反映 | テスト実施 / GitHubへの反映 |

### 11-2. 役割は「絶対的な禁止」ではありません

- Claudeが小さな機能追加をしてもかまいません。
- Geminiが軽微なバグを直してもかまいません。
- **状況に応じて必要な作業を行ってください。** ただし、大きく役割を外れる作業をする場合は、その旨を報告してください。

### 11-3. 基本の開発フロー

```
Gemini（新規作成・機能追加）
  ↓ commit & push
GitHub
  ↓ pull
Claude（不具合修正・原因調査）
  ↓ commit & push
GitHub
  ↓ pull
Gemini（ブラッシュアップ）
  ↓ commit & push
GitHub
  ↓ …以降くりかえし
```

**このリレーが成立する条件は、「前のAIが必ず push を完了していること」です。**（→ 第3章 3-2）

### 11-4. 引き継ぎの作法

- 作業を始めるAIは、**前のAIの最後のコミットメッセージを読んでから**作業してください。
- 作業を終えるAIは、**次のAIが読んで分かる粒度で**コミットメッセージと報告を書いてください。
- 「前のAIのコードが間違っている」と思っても、**勝手に大規模に書き直さない**でください。まず報告してください。

## 12. 既存コードを変更する前の確認

### 12-1. 変更前にやること

1. そのファイルが**なぜそう書かれているか**を読む（勝手に「無駄」と決めつけない）
2. 変更の影響範囲を確認する
3. **依頼された範囲だけを変更する**（ついでの改善は勝手にやらない）
4. 大きな変更が必要だと判断した場合は、**実行前に提案して確認を取る**

### 12-2. 上書き厳禁ファイル

以下のファイルは、**中身を読んで内容を保持したうえで**編集してください。丸ごと置き換えないこと。

## 13. 不明点がある場合のルール

### 13-1. 止まって確認すべきケース

- どのリポジトリ／どのアプリのことか分からない
- どのGCPプロジェクトか分からない
- 前のAIの未コミット・未push変更が残っている
- 依頼内容に複数の解釈があり、選択によって結果が大きく変わる
- 既存機能を壊す可能性がある変更が必要になった
- 秘密情報を扱う必要が出てきた
- デプロイ先・本番環境が特定できない

### 13-2. 確認の仕方

**プロジェクトオーナーはプログラミング初心者です。** 次を心がけてください。

- 専門用語を使う場合は、**かっこ書きで平易な説明を添える**
- 「どうしますか？」ではなく、**選択肢を2〜3個示して「どれにしますか？」**と聞く
- 各選択肢の**メリット・デメリット・リスク**を1行ずつ書く
- **推奨案を明示する**（「私のおすすめは A です。理由は〜」）
- 複雑な手作業を要求せず、**AI側でできることはAIがやる**

### 13-3. 確認せずに進めてよいケース

- 依頼内容が明確で、影響範囲が依頼の範囲内に収まる
- 既存の動作を壊さない
- 破壊的操作を含まない

この場合は、**作業を止めずに完遂し、結果を報告**してください。いちいち許可を求めて作業を止めないこと。

## 14. 破壊的操作の禁止事項

### 14-1. プロジェクトオーナーの明示的な承諾なしに実行してはいけない操作

**Git**
- `git push --force` / `git push -f`（他人の作業を消す）
- `git reset --hard`（手元の変更を消す）
- `git clean -fd`（未追跡ファイルを消す）
- `git branch -D`（ブランチを強制削除）
- `git rebase`（他人が使っているブランチの履歴を書き換える）
- リポジトリの削除・リネーム・可視性変更（public/private）

**Google Cloud**
- Cloud Run サービスの削除
- GCPプロジェクトの削除・請求先変更
- IAM 権限の削除・変更
- Secret Manager のシークレット削除
- 稼働中サービスのトラフィック切り替え

**Firebase**
- Firestore のデータ削除（`delete` 系の一括操作）
- セキュリティルールの緩和（`if true` への変更）
- Firebase プロジェクトの削除

**ファイル操作**
- `rm -rf` によるディレクトリ削除
- 既存アプリの大規模な書き換え
- 既存の設定ファイル・スキル・スクリプトの削除

### 14-2. 確認の取り方

破壊的操作が必要になったら、**実行前に止まって**次を報告してください。

```
【確認のお願い】
- やりたいこと : <操作内容>
- 対象         : <リポジトリ名 / GCPプロジェクト名 / サービス名>
- 理由         : <なぜ必要か>
- 失うもの     : <この操作で消えるもの>
- 元に戻せるか : 戻せる（方法: 〜） / 戻せない
- 代替案       : <より安全な方法があれば>

実行してよろしいですか？
```

### 14-3. 「元に戻せない操作」は特に慎重に

- Git の履歴書き換え、force push
- クラウドリソースの削除
- データベースのデータ削除

これらは**取り返しがつきません**。少しでも迷ったら実行しないでください。
