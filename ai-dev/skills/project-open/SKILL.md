# project-open スキル

## 目的

Gemini・Claudeが、既存アプリのリポジトリで作業を開始・終了するときに、
共通開発ルールと安全確認スクリプトを漏れなく実行するためのスキル。

このスキルは「何を確認すべきか」の判断を含むため、Scriptだけでは代替できない
（Scriptは機械的なチェックしかできない。「このアプリは何のアプリで、今回の
依頼と合っているか」を理解するのはAIの役目）。

## Trigger conditions（このスキルを使う場面）

- 既存アプリのリポジトリで作業を開始するとき
- 既存アプリのリポジトリでの作業を終えるとき
- Gemini/Claude間で作業を引き継ぐとき

新規アプリを立ち上げるときは、代わりに
`ai-dev/prompts/NEW_APP_LAUNCH_PROMPT.md` を使う。

## 手順

### 作業開始時

1. `pwd` で現在地を確認する
2. `git remote -v` で、依頼されたアプリのリポジトリと一致しているか確認する
   （類似名リポジトリの誤操作に注意。共通ルール第6章）
3. 次を読む
   - 共通開発ルール: `ai-dev/rules/DEVELOPMENT_RULES.md`
     （Cloud Shellでは `~/ai-dev/rules/DEVELOPMENT_RULES.md`）
   - このアプリの `CLAUDE.md` / `GEMINI.md`
4. 安全確認スクリプトを実行する

   ```bash
   ~/ai-dev/scripts/check-handoff.sh
   ```

   - `RESULT: NG` が出た場合は、**作業を開始せず**、内容を確認してから
     プロジェクトオーナーに報告する（前のAIの未コミット/未push変更がある可能性）
   - `RESULT: OK` であれば作業を開始してよい

5. 依頼内容が、読んだ固有情報（ブランド・UI方針・データ連携方針等）と
   矛盾しないか確認する。矛盾する場合は作業前に確認する。

### GCP/Cloud Runを扱う作業の場合

デプロイやGCPリソースの操作を行う前に、追加で次を実行する。

```bash
~/ai-dev/scripts/check-gcp-project.sh
```

- `NG` が出た場合は、**GCP操作を中止**し、現在のgcloudプロジェクトが
  正しいか確認する（別アプリのプロジェクトを誤操作する事故の防止）

### 作業終了時

1. 変更内容を実際に動かして確認する
2. 共通ルール第9章に沿ってテスト・ビルドを実施する
3. 意味の分かる単位でcommitする
4. 安全確認スクリプトを再実行し、pushまで完了しているか確認する

   ```bash
   ~/ai-dev/scripts/check-handoff.sh
   ```

   - `RESULT: OK` になるまで、作業は終了していない
5. Pull Requestを作成する（draft）
6. 次のAIへの引き継ぎ内容を報告する（編集したリポジトリ・ブランチ・
   push済みコミットのハッシュ。共通ルール第3-2章）

## このスキルが前提とする限界

`check-handoff.sh` は「その場で見える危険」しか検出できない。
前のAIがcommitすらしていない、あるいはcommitしたがpushしていない作業は、
どんな手段でも次のAIからは検出できない（共通ルール第3-3章）。

このスキルは「気づけるものは確実に気づく」ためのものであり、
「pushし忘れそのものを防ぐ」ものではない。最終的には、各AIが
「commitしたら必ずpushする」という運用を守ることが唯一の防御線である。
