# MCPサーバを作るときに踏む穴

実装して実機で繋ぐまでに実際に踏んだものだけ。仕様書を読んでも書いて
いない、あるいは読んでも気づけない種類のものを集めている。

## 1. ツール本体から例外を投げてはいけない

Python SDK は例外を包み、クライアントには
`"Error executing tool <name>"` という定型文だけを返す。**こちらが用意
した「有効なIDはこれ」「先に設定を確認せよ」といった情報は捨てられ、
サーバのログにしか残らない。**

結果としてモデルが自己修正できず、原因究明のたびに人間がログを見ることに
なる。失敗は必ず**戻り値**として返し、次に何をすべきかを添える。

```python
def _failure(message, *, hint=None, **extra):
    out = {"ok": False, "error": message}
    if hint:
        out["hint"] = hint
    out.update(extra)
    return out
```

全ツールを不正な引数で叩き、例外が出ないことを網羅テストで固定する。
ツールを増やしたらその表にも足す（足し忘れると落ちるようにしておく）。

## 2. `streamable_http_app()` の既定がローカルだけ通す

Python SDK の `streamable_http_app()` は `host` 引数の既定が
`"127.0.0.1"` で、**その場合だけ DNS リバインディング対策を自動で
有効にし、許可する Host を localhost だけにする。**

```
Host: 127.0.0.1:34271          -> 400 Missing session ID   （MCP層に到達）
Host: <本番のホスト名>          -> 421 Invalid Host header
```

- **ローカルの疎通確認では絶対に出ない**
- 応答本文は `Invalid Host header` の一行だけで、直し方が書かれていない
- 421 は他の意味でも使われるため、原因が推測しにくい

対策は host を明示するか、検査を自前の層に移して**拒否された値と直すべき
設定名を返す**こと。クラウドの実行環境は1つのサービスに複数のホスト名を
割り当てることがあるので、Host を認可の条件にするなら列挙漏れに注意する
（公開HTTPSでは Host 検査は防御になっておらず、実際の境界はトークン）。

## 3. 可逆性でツールを分け、機械可読にする

判定基準は1つ。

> 自分の名前で、外から見える形で、静かには取り消せないものを作るか

| 階層 | 例 | 注釈 |
|---|---|---|
| 1 | 参照・検証・プレビュー | `read_only_hint` |
| 2 | 下書き保存・試し書き | `idempotent_hint`（可逆） |
| 3 | 人間の承認が必要なもの | `destructive_hint` |

**不可逆な操作そのものをツールとして公開しない。** 公開するのは
「承認を申請する」ツールだけにし、実行は承認成立後にサーバ内部から
呼ばれる内部関数に閉じる。そうしておけば、**トークンが漏れても不可逆な
操作はされない。**

## 4. 公開しているツールの一覧を、人間が読める形で持つ

手順書の表が黙って古くなると、**公開しているつもりのないツールに
気づけない。** 表をパースして実装と突き合わせるテストを書く。

実際に、実装16ツールに対して表が12行、説明文が「15ツール」という
状態になっていた。

## 5. Gemini アプリ（Connected Apps）から繋ぐ要件

**MCPサーバ自身が認可サーバでなければ接続しない。** 外部の認可サーバを
広告しても進まない。これが分かるまで1日かかった。

詳細と、実機で通った要求の並びは `references/gemini-connected-apps.md`。

## 6. stdio とリモートでツール実装を共有する

トランスポートだけが違う別物として作ると、片方だけ直す事故が起きる。
ツールの実装は1つにして、アダプタを2つ用意する。

そのうえで、**両方のトランスポートで同じ検証を走らせる。** 片方の
テストクラスを継承してもう片方で再実行する形にすると、アダプタの
取り違え（ボディの読み方、クエリの渡し方、ヘッダ名の大文字小文字）が
出てくる。実際にヘッダ名の扱いの違いがこれで見つかった。

## 7. リモートの `/mcp` は認証が未設定なら拒否する

公開インターネット上のエンドポイントであり、そこからリポジトリ作成の
ような操作ができてしまう。**設定漏れが「素通り」として現れる実装が
最も危険**なので、既定を拒否にする。

401 を返すときは `WWW-Authenticate` に保護リソースメタデータの場所を
添える（クライアントが認可の入口を見つけられる）。

なお認証ミドルウェアは**ルーティングより外側**に置く。内側に置くと、
未認証の相手にホスト許可リストのような内部設定が見える。
