# 落ちることを確認した検証だけを信じる

検証を追加したら、**それがわざと壊した状態で落ちることを見せる。**
落ちるところを見ていない検証は、何も検証していない可能性がある。

この規律が無かったために、2日間の開発で10件の見逃しが起きた
（`references/incidents.md` に実例）。内訳は「落ちない確認を確認として
報告した」5件と「設定は正しく見えるのに動かなかった」5件である。
どれも**検証は緑だった。**

## 手順

検証（テスト・診断・確認スクリプト）を追加・修正するたびに、4つとも行う。

1. **検証を書く**
2. **わざと壊す。** 検証が守っているはずの性質を、実際に壊す
   （該当行を消す、ヘッダを外す、値を空にする、依存を抜く）
3. **落ちることを確認する。** 落ちなければ、その検証は捨てて作り直す
4. **元に戻して通ることを確認する。** 両方の出力を報告に載せる

3 を飛ばすと、後から「テストがあるのに壊れていた」という形で出てくる。
そのときには原因が2つある（実装の不具合と、検証の不具合）ので、
切り分けから始めることになる。

壊し方が思いつかないときは、その検証が何を守っているのかが自分でも
分かっていない。書き直す。

## 書いてはいけない判定

### 否定形で合格を決める

```
# 悪い: 401 でなければ認証は通っている
if ($status -ne 401) { Ok "authenticated" }
```

421 も 500 も合格になる。**実際に 421 が「OK」として報告された。**

期待する成功を正面から書く。

```
# よい: 本番と同じ要求を投げ、200 とセッションIDを要求する
if ($status -eq 200 -and $headers["mcp-session-id"]) { Ok }
```

### 「存在する」「読める」で止める

- 鍵が**パースできた**で ok を返す → 実際には**署名できず**送信が失敗した
- シークレットが**登録されている**を確認 → 中身は改行1文字だった
- 保存先が**設定されている**を確認 → 書き込み権限が無かった
- エンドポイントが**200を返す**を確認 → ハンドシェイクは成立しなかった

診断は**本番と同じ経路を一度通す**。鍵なら署名する。保存先なら書いて
読んで消す。API ならプロトコル上の最初の往復まで行う。

### 対象そのものを見ずに、周辺を見る

```
# 悪い: 別オリジンの iframe の contentDocument が null であることを確認
#       → ヘッダの有無に関係なく null になる。何も検証していない
```

「この検証は、守りたい性質が無い状態と、ある状態を区別できるか」を
毎回問う。区別できないなら手順 3 で落ちないので、そこで気づける。

### 環境に依存する既定値で「通った」と見なす

- 依存が入っていない環境で `OK (skipped=87)` を OK と読んだ。**本番で
  動くトランスポートのテストが、2日間まるごとスキップされていた**
- ローカルの疎通確認だけで通した。SDK が `host="127.0.0.1"` の場合だけ
  保護を自動で有効にしており、**公開ホスト名でだけ落ちた**

スキップ件数は毎回読む。減らせるなら減らして走らせる。
「ローカルでは通る」は、本番で通ることの証拠にならない。

## 人間に実行させる確認スクリプト

- **失敗したときに必ず非ゼロで終わる。** 途中の失敗を握り潰さない
- 各段階で「何が確認できたか」を出す（長さ、一致、HTTPコード、コミット）
- 手順の自己申告を根拠にしない。**確認の主体を、確認される側に移す**
  （例: デプロイ後にスクリプトが「デプロイした」と言うのではなく、
  稼働中のサービスに「どのコミットで動いているか」を聞く）
- 秘密情報は値ではなく**長さと形**を出す

## 分からないことを「大丈夫」に丸めない

確認できなかった項目は、三値で持つ。

| 値 | 意味 |
|---|---|
| ok | 確認して問題なかった |
| ng | 確認して問題があった |
| **unknown** | **確認できなかった。理由を添える** |

`unknown` を ok に丸めると、診断が嘘を言う。`ng` に丸めると、本当の
障害が埋もれる。別の値として持ち、画面にも戻り値にもそう出す。

同じ理由で、**自分のログに出ないこと＝起きていないこと、と扱わない。**
相手側で完結する処理は、こちらのログには現れない。

## 報告するとき

- 実際に走らせた出力を見せる。走らせていないなら、走らせていないと書く
- 「落としてから直した」ことを書く。手順 2〜3 を踏んだ証拠になる
- 検証できなかった範囲を明示する（環境上できなかったことと、やらな
  かったことを区別する）

## チェックリスト

検証を追加したら、報告の前に:

- [ ] わざと壊して落ちるところを見た
- [ ] 元に戻して通るところを見た
- [ ] 否定形（「〜でなければOK」）で合格を決めていない
- [ ] 「存在する/パースできる」で止めず、本番と同じ経路を通した
- [ ] スキップ件数を読み、減らせるものは減らした
- [ ] 確認できなかった項目を ok に丸めていない
- [ ] 失敗したときに非ゼロで終わる

## 実例

`references/incidents.md` に10件。それぞれ「何を確かめたつもりで、
実際は何を確かめていたか」を書いてある。新しい型を踏んだら追記する。
